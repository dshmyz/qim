# 群共享 - RealtimeSession 落地清单

> 目标：把「群里某个成员共享屏幕给全体看」这套实时会话（`RealtimeSession`）机制真正跑通。
> 当前状态：链路断点在前端「接线」，后端代码大部分已就绪。本文档给出精确到文件/函数/字段的落地清单、风险与回滚点，供排期与决策。

---

## 一、背景与现状结论（已核实）

### 这套机制本来是干嘛的

一个「多对象屏幕共享」的授权-参会会话模型：

```
发起者 → realtime:session:create（写库 realtime_sessions）
      → 广播 realtime:session:created
全体成员 → 收到后 join/直接拉流
      → WebRTC 1 对 N 观看（realtime:webrtc:*）
发起者 → realtime:session:ended → 全体断开
```

### 现状：断链 + 多套信令并存

- **前端有完整消费逻辑**：`RealtimeConnectionManager`（发起端 1 对 N）、`RealtimeViewerConnection`（观看端）、`realtimeStore`、ChatWindow/Main 的接收分支均已存在。
- **但整条链路的起点（创建会话）没有任何触发源**：
  - WS `realtime:session:create`：前端**从不发送**
  - HTTP `POST /api/v1/realtime/sessions`：前端 **0 调用**
- **前端存在三套互不对齐的 WebRTC 信令**：

| 层 | 消息类型 | 位置 |
|----|---------|------|
| 点对点信令 | `webrtc.offer` / `webrtc.answer` / `webrtc.ice-candidate`（点号，`signal` 字段） | `useSignaling.ts` + 后端 `handleWebRTCSignal` |
| 连接层 | `webrtc_offer` / `webrtc_answer` / `webrtc_ice_candidate`（下划线，`signal` 字段） | `utils/realtimeConnection.ts` |
| 会话内信令 | `realtime:webrtc:offer/answer/ice`（冒号，`offer`/`answer`/`candidate` 字段） | 后端 `HandleRealtimeWebRTCOffer/Answer/Ice` |

### 已知纠偏

- 早期判断「后端缺 `realtime:webrtc:*` 转发」**不实**。核实结果：后端**两套 WebRTC 转发都已完整实现**，会话内转发还会校验 participant 身份（`status IN approved/joined`）。
- `RealtimeSession` 表当前**为空**：两条写库通道（WS 创建 / HTTP 创建）前端均未触发。正常用户操作不会落数据。

## 三、前端 —— 主要工作（按依赖顺序分 5 层）

### 第 1 层：WebRTC 信令协议对齐（铁丝网）

- **文件**：`qim-client/src/utils/realtimeConnection.ts`
- **类**：`RealtimeConnectionManager`（发起者）、`RealtimeViewerConnection`（观看者）
- **动作**：
  - 收发类型从 `webrtc_offer`/`webrtc_answer`/`webrtc_ice_candidate`（下划线）改为后端会话内协议 `realtime:webrtc:offer/answer/ice`（冒号）
  - 字段从 `signal` 改为 `offer`/`answer`/`candidate`，并补 `session_id` + `target_user_id`
  - 三层信令统一为后端这层冒号协议（点对点 `webrtc.*` 保留给通话）
- **风险**：低（纯收发字符串，可保留旧函数签名）
- **回滚**：保留旧签名，切换调用点

### 第 2 层：发起端触发创建 + 推流（核心缺口）

- **文件**：`qim-client/src/components/realtime/RealtimeCommunication.vue` / `qim-client/src/views/Main.vue`（屏幕共享发起 emit 链）
- **动作**：
  - start 时发 `realtime:session:create`（或 HTTP `POST /sessions`）拿 `session.id`
  - `manager.setSessionId(sessionId)` + `manager.setLocalStream(stream)`
  - 每个观看者加入时 `manager.createConnectionForViewer(viewerId)` 建连接
- **风险**：**中**（动到现有屏幕共享入口）
- **回滚**：后端开关 / 前端保留旧 1v1 路径

### 第 3 层：观看端直接拉流（砍审批）

- **文件**：`qim-client/src/components/chat/ChatWindow.vue`
- **动作**：
  - 删掉 [1639-1668](qim-client/src/components/chat/ChatWindow.vue:1639)「自动 requestJoin → 等 approve」流程
  - 收到 `realtime:session:created` → `viewerConnection.setSessionId()` + 主动发起 offer 拉流
  - 收到 `realtime:webrtc:offer` → `viewerConnection.handleOffer(...)`（对齐 payload 字段）
- **风险**：中（删除审批分支）
- **回滚**：可保留审批分支，开关切换

### 第 4 层：群内共享 UI（新增）

- **文件**：新建组件 + 接入 `realtimeStore` 状态
- **动作**：「正在共享」横幅/入口（现仅一条 `$message.info` toast）+ 可选已加入观看者列表
- **风险**：低（纯新增）
- **回滚**：移除组件

### 第 5 层：结束 / 异常 / 生命周期

- **文件**：`ChatWindow.vue`（`session:ended` / `participant:left` 处理）+
- **动作**：对齐 `realtime:session:ended`、`realtime:participant:left` 处理；发起者掉线兜底
- **风险**：中（边角 bug 多）
- **回滚**：逐项测试

## 四、生效范围控制（已讨论确认）

- **只打通「屏幕共享」，不改通话**：视频/语音通话继续走 `call.*` + 独立的 `useRealtimeCommunication` 实例。这是 scope 红线，回归测试硬指标。
- **砍掉审批流**：既然是「共享给全体看」，`requestJoin / join:requested / join:approved / approveJoin` 这一大段整体废弃，链路缩短。
- **首批不做 SFU**：1 对 N 用发起者对每观看者各建一条 RTCPeerConnection。代价是发起者上行带宽 = 分辨率 × 人数，人数上来再演进 LiveKit/mediasoup。
- **首批不做断线重连的状态恢复**：标注为已知限制，后续版本补。

## 五、总体风险评估

> 前后端代码 80% 已存在，本次主要是「接线 + 协议统一」。失败的最坏情况是回到「不跑」的现状，不会比现在更差。

- **主要风险不在「会不会搞坏」**，而在「作用域会不会越界弄坏正在用的 1v1 共享/通话」。用「保留旧路径 + 后端开关」锁住。
- **建议推进顺序**：第 1 层 → 第 2 层 → 第 3 层 → 第 4 层 → 第 5 层，每层独立可上线、可回滚。
- **回归基线**：改造前后验证「现有通话 + 现有 1v1 屏幕共享」仍可用。

## 六、RealtimeSession 表的去留（重要设计点，落地时定）

**结论：落地本身需要这张表，但"留多少"取决于免审批做多彻底——本项尚未定，落地第 2~3 层时再定。**

落地后这张表承载的实际用途：

1. **状态来源**：记录当前谁在共享、共享什么（`initiator_id` + `type` + `status`）；"群里现在有没有人正在共享"就是查它。
2. **WebRTC 转发权限闸门**：`HandleRealtimeWebRTCOffer/Answer/Ice` 会校验 `participant.status IN (approved, joined)` 才转发（`ws/realtime.go:550`）。删表 = 转发校验失效。
3. **去重**：`HandleRealtimeSessionCreate` 用 `status IN (pending/active)` 防止同群开多个共享。
4. **审计/历史**：谁何时共享过。

**关键分叉**：我们已定"共享给全体看 → 砍审批流"。但后端 WebRTC 转发基于 `participant` 的 `approved/joined` 状态，因此：

- **保留参与者/审批授权模型** → 表必须原样保留。
- **彻底免审批、不登录参会人、不存 participant** → WebRTC 转发要改为非成员校验，表只剩"当前共享会话"单条状态，可精简字段或改内存态。

**建议**：落地时**先原样保留**（零改动即可用），跑通后根据审批砍多干净，回头决定是**保留原模型 / 精简字段 / 降级为不持久化**。现在动表结构会提前锁死设计。
