# 机器人文件消息处理方案分析

> 状态：方案讨论稿，暂未实施
> 日期：2026-08-03

## 问题背景

当前用户在普通聊天界面或 bot 会话中给机器人发送文件/图片时，AI 子系统会收到一段看不懂的 JSON 字符串（文件消息的 content 格式为 `{"url":"...","id":123}`），导致一系列问题：

### 现状路径

1. **bot 会话（1v1 AI 助手）**
   - [message_service.go:179-180](../qim-server/service/message_service.go#L179-L180) 只判断 `convType == "bot"`，不判断消息类型，无差别触发 `handleBotMessage`
   - [message_service.go:309-318](../qim-server/service/message_service.go#L309-L318) 把历史消息的 `msg.Content` 原样塞进 AI 上下文，AI 看到 `{"url":...,"id":...}` 困惑回复

2. **普通会话（群聊/讨论组）**
   - [routes.go:148-162](../qim-server/app/routes.go#L148-L162) 的 `OnMessageSent` 回调只接收 content 字符串，丢失 msgType 信息
   - 触发三个问题：
     - 待办提取（[message_handler.go:260](../qim-server/handler/message_handler.go#L260)）：把 JSON 喂给 `todoExtractor`，浪费 AI 调用或误抽待办
     - 分身记忆（[smart_reply_handler.go:118](../qim-server/handler/smart_reply_handler.go#L118)）：JSON 写进分身记忆库，污染主人画像
     - 意图检测（[smart_reply_handler.go:193](../qim-server/handler/smart_reply_handler.go#L193)）：对 JSON 做意图检测不可控，可能误触发无意义回复

### 根本症结

消息回调链路（`OnMessageSent`、`handleBotMessage`、`TryExtractTodos`）全部只拿 `content` 字符串，丢掉了 `msgType` 信息。文件、图片、分享卡片等非文本消息的 content 都是结构化 JSON，被当成普通文本一路喂给 AI 子系统。

## 三层方案

### 第一层：止血（必做）

在所有 AI 子系统入口判断消息类型，对非文本消息跳过处理。

**改动点**：

1. 扩展 `OnMessageSent` 回调签名，增加 `msgType` 参数
   - 涉及：[ws.go:100](../qim-server/ws/ws.go#L100)、[ws.go:845](../qim-server/ws/ws.go#L845)、[message_service.go:208](../qim-server/service/message_service.go#L208)、[routes.go:148](../qim-server/app/routes.go#L148)、[service_test.go:502](../qim-server/service/service_test.go#L502)
   - **注意**：WebSocket 路径要确认前端 ws 消息体里有 type 字段

2. `OnMessageSent` 回调里按类型分流：
   - `text` / `markdown`：正常走 `TryExtractTodos` + `HandleMessage`
   - `file` / `image` / 其他：跳过

3. `handleBotMessage` 入口加判断：非文本消息直接 return（**但 external_webhook 模式要例外**，见风险章节）

**跳过条件设计**：用"消息类型不是 text/markdown **且** content 里没有 mention token"才跳过，而不是单纯按 type 跳过。避免未来"文件 + 附带文字说明 + @"场景被误杀。

### 第二层：bot 会话交互合理化（应做）

第一层之后，bot 会话会出现新问题：用户发文件给机器人，机器人完全沉默，用户以为卡了。

**方案**：把文件消息转成人类可读描述再喂给 AI，例如：

```
[用户发送了一个文件：季度报告.pdf，大小 1.2MB]
```

AI 据此给出合理回复，如"收到您发送的文件《季度报告.pdf》，但我目前无法查看文件内容..."

**实现要点**：
- `handleBotMessage` 里对 `file` 类型，从 content JSON 解析出文件名、大小，拼成描述字符串作为 user message
- **历史消息回放必须同步转换**（[message_service.go:309-318](../qim-server/service/message_service.go#L309-L318)），否则上下文里新老混用更混乱
- 描述里要明确"无法查看内容"，避免 AI 幻觉自己打开了文件

### 第三层：真正解析文件内容（暂不做）

#### 图片（基础设施已存在，缺的是复用）

**现状**：
- [types.go:8](../qim-server/ai/types.go#L8) Message 已支持 ImageURL，MarshalJSON 自动转多模态格式
- [types.go:162](../qim-server/ai/types.go#L162) TaskTypeVision 已定义
- [ai_text_handler.go:270-292](../qim-server/handler/ai_text_handler.go#L270-L292) 图片翻译已跑通这套机制

**缺四块**：
1. [config.yaml:48-69](../qim-server/config.yaml#L48-L69) routes 缺 `vision:` 配置项
2. 视觉能力探测没抽出来（[ai_text_handler.go:243-256](../qim-server/handler/ai_text_handler.go#L243-L256) 硬编码 `visionProviders`），应抽成 `AIService.HasVisionCapability()`
3. `imageToDataURL` 等工具函数困在 handler 包，需下沉到 ai 包
4. `handleBotMessage` 不判断"这条该走视觉"，要按消息类型分支并用 `TaskTypeVision`

#### 二进制文件（从零做）

三种路线：

| 路线 | 描述 | 优点 | 缺点 |
|------|------|------|------|
| A. 纯文本提取 | txt/md/csv 直接读，PDF/Word/Excel 用解析库 | 不依赖多模态，普通 chat 模型可用 | 扫描件、图片型文档提取不出文本 |
| B. AI 文件解析 API | Anthropic document type、阿里通义 file 接口 | 解析质量高 | 各 provider 接口不同，要适配层 |
| C. 转图片 + 视觉模型 | 每页转图片用视觉识别 | 复用已有视觉能力，覆盖面广 | 成本高、速度慢、长文档 token 爆炸 |

**建议**：路线 A 起步，只覆盖 txt/md/csv/code/pdf/word/excel，其他格式回退到"告知不支持"。

## 风险分析

### 第一层风险

#### 1. 接口签名变更影响面

`OnMessageSent` 加 `msgType` 参数涉及 5 处改动。

**关键风险**：WebSocket 路径（[ws.go:845](../qim-server/ws/ws.go#L845)）当前只传 content，要确认 ws 消息体里有 type 字段。如果前端 ws 消息没传 type，止血逻辑失效。

#### 2. external_webhook 模式被误伤

[message_service.go:262](../qim-server/service/message_service.go#L262) external webhook bot 把 content **原样透传**给外部 agent。外部 agent 可能自己有能力处理文件，一刀切跳过非文本消息会让它收不到文件消息。

**对策**：internal_ai 和 external_webhook 两条路径分别处理。

#### 3. "文件 + @"误杀

当前前端发文件时 content 是纯 JSON，不带 mention token，跳过是安全的。但这是偶发结果不是设计保证。

**对策**：跳过条件用"非文本且无 mention token"。

### 第二层风险

#### 1. 历史消息回放一致性

[message_service.go:266](../qim-server/service/message_service.go#L266) 拉最近 20 条历史消息塞进上下文。如果只转换当前消息不转换历史消息，上下文新老混用更混乱。必须同步转换，工作量和测试面翻倍。

#### 2. 描述格式陷阱

`[用户发送了一个文件：xxx.pdf]` 这种描述，AI 可能幻觉自己打开了文件。需要在描述里明确"无法查看内容"，但这又会让 AI 千篇一律拒绝。

#### 3. 老数据兼容

DB 里已存大量 `type=file` 且 content 是 JSON 的历史消息。靠 msgType 字段判断是可靠的，但要确保回放查询时把 type 一起查出来（当前 `Find(&messages)` 会带出来，这点 OK）。

### 第三层风险

#### 图片

1. **成本**：视觉模型调用比文本贵 5-10 倍，bot 会话发图就触发，没有限频
2. **token 爆炸**：dataURL 是 base64，比原图大 33%。历史回放拉 20 条，若有多张图每次都重发，token 爆炸
3. **历史图片策略**：要么"只带最近 1-2 张图，更早的转描述"，要么"图片消息不进历史回放"
4. **图片 URL 访问**：bot 收到的是 `/static/...` 相对路径，要下载转 dataURL。下载失败、超时、404 要有兜底
5. **大图片保护缺失**：[ai_text_handler.go:237](../qim-server/handler/ai_text_handler.go#L237) 的 `dataURLTooLarge` 只在图片翻译接口用，bot 路径没有任何大小保护
6. **多模态格式兼容性**：[types.go:14-34](../qim-server/ai/types.go#L14-L34) MarshalJSON 只生成 OpenAI 格式 `image_url`。若 vision 路由配了 anthropic，它用 `source` 字段，格式不兼容会失败

#### 二进制

1. **解析库是攻击面**：PDF/Word/Excel 解析库历史上有大量 CVE。恶意文件可触发 zip bomb、XXE、OOXML 解析栈溢出，可能 RCE。**这是安全红线**
2. **zip bomb**：1MB zip 解压成 10GB，OOM 打挂服务。docx/xlsx 本质是 zip
3. **XXE**：docx/xlsx 是 XML，解析库不禁用外部实体可读服务器任意文件
4. **临时文件泄漏**：下载、解析要写临时文件，panic 或异常退出不清理，磁盘填满
5. **token 上限**：长文档提取出几万字，塞进上下文爆 token。要摘要又得一次 AI 调用
6. **类型白名单不可靠**：靠扩展名判断可被改后缀绕过；靠 magic number 更准但实现复杂
7. **扫描件死局**：扫描版 PDF 提取不出文本，用户以为能看其实不能，体验比"不支持"更差
8. **性能阻塞**：大文件解析阻塞 bot 回复协程，AI 调用 60s 超时（[message_service.go:325](../qim-server/service/message_service.go#L325)），解析慢会超时

## 三个最容易被忽略的风险

### 1. external_webhook 模式需要区别对待

止血和转换描述的逻辑都不能一刀切应用到 external_webhook 模式。外部 agent 可能自己能处理文件，原样透传更合理。这会让"在 handleBotMessage 入口判断"的简单方案变复杂——要分 internal_ai / external_webhook 两条路径分别处理。

### 2. 历史消息回放是一致性陷阱

任何对当前消息的转换，都必须同步应用到历史消息回放，否则上下文混乱。这点最容易在实现时漏掉，测试也难覆盖（要构造"历史里有文件消息 + 当前发文件消息"的场景）。

### 3. 二进制解析的安全边界不是可选的

图片解析的风险是成本和体验，二进制解析的风险是**安全**。不做大小限制、类型校验、解析库沙箱化，就是给用户一个上传恶意文件攻击服务器的入口。安全边界的实现成本比解析逻辑本身还高。

## 建议

| 层级 | 风险 | 建议 |
|------|------|------|
| 第一层 止血 | 可控 | 做，注意 external_webhook 区别对待 + 跳过条件用"非文本且无 mention token" |
| 第二层 合理交互 | 中等 | 做，主要工作量在历史消息回放一致性 |
| 第三层 图片 | 中等偏上 | 如果做，必须先设计历史图片回放策略 + 限频 + 大小保护，不能直接复用图片翻译的 dataURL 方案 |
| 第三层 二进制 | 高 | **先不做**，第二层的"告知不支持"已能覆盖，等有明确且高价值的使用场景再投入 |
