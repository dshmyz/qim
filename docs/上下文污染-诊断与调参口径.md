# 分身与群助手「上下文污染」诊断与调参口径

> 适用：分身(avatar) / 群助手(group assistant) 被自身回复污染的历史组装优化。
> 本文是**观测口径**文档——告诉你怎么读诊断日志、怎么判断该不该调 `selfTurnWindow`、调到多少。配合代码 `service/context_hygiene.go`。

## 一、这次优化解决了什么

把"自身(AI)回复"按时间窗切成两档，避免一对自相矛盾的问题：

| 场景 | 问题 | 一刀切后遗症 |
|---|---|---|
| **分身** | 历史排除掉自己的回复 → 追问"你刚说的"接不上（**失忆**） | 若全部保留又会自我复读 |
| **群助手** | 远期自己的回复原样回灌 → 照着旧话复读、回复固化（**自我复制**） | 若全部排除又会失去多轮指代 |

**方案**：`selfTurnWindow = 15min`。
- 窗口内（近期）自身回复 → 保留为 assistant 轮次（多轮指代锚点）。
- 窗口外（远期）自身回复 → 折叠成一句概要追加到 system-note（可索引、不原样复读）。

## 二、诊断日志口径

日志统一前缀 `[ContextDiag]`，共 4 个打点、3 个 label：

| label | 位置 | 说明 |
|---|---|---|
| `群助手/buildHistory` | `service/smart_reply_graph.go`（`buildHistoryMessages`） | 群助手流式/工具路径 |
| `群助手/graph` | `service/smart_reply_graph.go`（`createHistoryNode`） | 群助手 Execute（非流式）路径 |
| `分身/历史` | `service/avatar_reply_graph.go`（`getConversationHistory`） | 分身历史组装 |

### 通用行格式（群助手两个 label）
```
[ContextDiag] 群助手/buildHistory conv=20 注入=5 自身回复=2 (近期=1 远期=1) token~31
```
| 字段 | 含义 | 关注点 |
|---|---|---|
| `注入` | 注入 prompt 的消息总条数 | —— |
| `自身回复` | 其中自身(AI)回复条数（assistant+avatar） | 占比过高 = 潜在自我复制 |
| `近期/远期` | 窗口内/外各自身回复(≤15min / >15min) | **核心观察字段** |
| `token~N` | 估算 tokens（约 3 字符/token） | 污染占用成本 |
| `无历史注入` | 该会话没有可注入历史 | 用于区分"真空"与"忘统计" |

### 分身 label 的追加行
```
[ContextDiag] 分身/历史 conv=10 avatar总=6 保留=2 已滤=4
```
| 字段 | 含义 | 关注点 |
|---|---|---|
| `avatar总` | 会话里全部分身回复条数 | —— |
| `保留` | 窗口内保留的近期分身回复 | 保留≈0 而 总>0 → 仍可能失忆 |
| `已滤` | 被滤掉的**远期**分身回复 | 远期为0 且 保留=0 → 排查是否过滤逻辑失效 |

## 三、判断"要不要调 selfTurnWindow"

`selfTurnWindow = 15min` 是**初值，非标定值**。上线后按下列特征判断：

### 1）窗口太短（该保留的近期回复被误判为远期 → 复现失忆）
出现特征：
- 用户**短时间内追问"你刚说的 / 上一个 / 你提的那个方案"**，分身/助手答不上来或答错。
- 日志里 `分身/历史` 的 `已滤` 数值偏大，且被滤的多是**几分钟前**的自回复。
- 群助手侧：用户接着自己上一条 AI 回复追问，但历史里那条没进 assistant 轮次。

→ **调大**：如 `30 * time.Minute`。

### 2）窗口太长（远期回复仍被当成"近期锚点"回灌 → 自我复制仍在）
出现特征：
- 群助手仍频繁**复读**十几、二十几分钟前自己的话。
- 日志里 `远期=0`，但你自己知道有 20 分钟前的自回复在历史里（说明它被当成近期了）。
- `自身回复` 占比居高不下，token 占用大。

→ **调小**：如 `10 * time.Minute`。

### 3）黄金准则
**观察"近期=保留的指代锚点是否够用"与"远期=是否还有自我复制"两个指标的对冲**。理想状态是：
- 所有用户会追问的近期自回复都在 `近期` 里（不误滤）；
- 所有"过时自回复"都进了 `远期` 并被折叠（不复读）。

若两者无法同时满足，优先保住**近期锚点**（失忆比复读更伤体验），窗口先偏大，再逐步调小。

## 四、怎么改

只改一处常量：`service/context_hygiene.go`

```go
const selfTurnWindow = 15 * time.Minute // ← 调整此值
```

改完跑回归：
```bash
cd qim-server
go test ./service/ -count=1 -run 'TestSegmentHistory|TestIsNearSelf|TestFoldFarSelf|TestBuildHistoryMessagesWindowed' -v
```

> 注意 `TestSegmentHistoryNearFarBounds` 用"略小于 / 略大于窗口"构造边界，改窗口后该测试**不依赖具体数值**，仍会通过——它锁的是判定逻辑，不是 15min 这个数。

## 五、测量什么才叫"改对了"

一个会话级观察法（人工抽几个高频被追问的场景）：
1. 先看日志：`近期/远期/自身回复` 长什么样、`分身/历史` 的 `保留/已滤` 长什么样。
2. 实测兜底验证，去重放下面三类对话：
   - **复读音条**：旧消息里有助手/分身说过"方案A可行"，新讨论后助手是否还复读？→ 已折叠的远期应不复读。
   - **追问接续**：用户说"你刚说的那个方案呢" → 近期锚点应让它接上。
   - **超知识范围静默**（分身）：无知识命中时是否仍按配置静默（与本文无关，顺带确认没被误改）。
3. 改完一档，重放这三类，对比前后差异是否朝预期方向走。

## 六、与周边机制的关系（别混淆）

- **知识库检索 / 群知识 / 记忆**：注入的是"外部知识"，与"自身回复折叠"正交。折叠只动历史里的自身回复，不动这些注入段。
- **分身硬静默门控**（`prepare` 里的 `hasKnowledge` 判断）：只依据笔记/群知识/记忆命中，**不看历史**。改窗口不影响该门控。
- 本次未改 `Token 截断 / 轮次上限`（"只保留20轮是否够"是另一个话题，未动）。
